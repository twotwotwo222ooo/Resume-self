Q1：在首次跑通后，发现调试输入简历后，输出评分及其效果差，如何改进这个问题？

A1：六个维度的评分没有标准，添加提示词并打上问题锚点来增加置信度。

Q2：PDF的文本提取用的什么办法，怎么判断其提取的效果？

A2：在查看简历时可能会报错，提取和调用模型都可能成功，此时可能是哪里有问题？

Q3：可能 json.loads 提取时发现非法符号,报告文本没法当成 JSON 解析，审查就失败了。刷新后再传一次，有时能过（模型每次输出不完全一样）。需要改成按 schema 做结构化输出，或解析失败时自动修 JSON / 重试。



**常见问题及其解法：** 结果不理想，主要是因为现在是 **一次 Flash 调用同时打分、找问题和写评语**，细则偏定性，岗位信息也经常不够。建议按下面分层改，先改提示和链路，再动模型和解析。

## **1. 先改提示与评分尺（成本最低）**

当前六维只有一句话定义，模型容易把分数挤在 70–85，评语空泛。

- **给每维打分锚点**：例如 90/70/50/30 各对应什么证据（有设计取舍、只堆技术名词、纯职责罗列等）。
- **强制「证据句」**：每个分数必须引用 `[锚点]`，没有锚点不得给高分。
- **问题条数和优先级配额**：例如 high 不超过 5 条、总共 8–12 条，避免要么太少要么流水账。
- **改写必须出「原句 → 改后句」**，并带可量化数字的示例，禁止「建议更加具体」。
- **按候选人层级校准**：校招/实习/社招中级/高级用不同尺子，避免用高级标准打实习简历。
- **无 JD 时不要假装匹配**：技术匹配度固定降权或单独标注「通用评估」，避免乱猜岗位。

## **2. 把「一条链路」拆成多步**

现在 `extract_pdf → 一次 review_llm → validate`，质量和稳定性都绑在一次 JSON 上。

建议拆成 3–4 个节点：

1. **结构化理解**：模块、项目、每条 bullet、技术栈。
2. **对照 JD 抽要求**：必会技能、加分项、年限/领域。
3. **诊断与改写**：只针对 bullet 出问题。
4. **汇总打分**：基于前面证据打分，不再从头读全文瞎打。

校验失败就 **只重跑失败那一步**，不要整份重生成。

## **3. 模型怎么用**

`deepseek-v4-flash` 适合分类和抽取，不适合写招聘级改写。

- 抽取/打分用 Flash。
- 改写、综合评语用 **Pro / 更强模型**（或 Flash 开 thinking）。
- 关键步骤加 **few-shot**（好简历/差简历/改写前后各 1–2 例）。
- 需要稳定 JSON 时用 **结构化输出（schema）**，不要只靠 `json_object`。



## **4. 简历解析要先变准**

锚点错了，后面诊断都会飘。

- 补 **双栏/表格 PDF** 的阅读顺序，必要时上 OCR。
- 扩展标题识别：英文 `Experience`/`Projects`/`Skills`，以及「实习/项目」混排。
- 抽 **时间、公司、职位、技术词、数字**，给模型结构化输入，而不是一篇带锚点的长文本。
- 前端可展示「解析出的文本」，方便判断是解析差还是模型差。



## **5. 岗位匹配做成可解释项**

没有 JD 时，技术匹配度水分最大。

- 把 JD 拆成技能清单，输出 **覆盖 / 部分覆盖 / 缺失**。
- 匹配分 = 覆盖率，并列出「简历有但 JD 没有」的噪音技能。
- 允许维护 **岗位画像**（后端、前端、算法），无 JD 时用画像，不再用「通用软件研发岗」。
- 综合分与岗位匹配分分开展示，避免两个 80 分含义不同。



## **6. 分数和展示**

- 权重可按岗位调整：后端加重项目深度/技术匹配，应届加重结构/表达。
- 增加 **校准**：同岗位样本上对齐人工分，减少虚高。
- 报告增加：技能缺口表、改写对照、优先改哪 3 条。优先级改成中文（高/中/低）。



## **建议落地顺序**

1. **提示词 + 分数量规 + 改写对照**（1–2 天，立刻能感到具体）。
2. **拆图：抽取 → 诊断 → 打分**，校验失败重试。
3. **解析增强 + JD 技能对齐**。
4. **Flash / 强模型分工，必要时换强模型做改写**。
